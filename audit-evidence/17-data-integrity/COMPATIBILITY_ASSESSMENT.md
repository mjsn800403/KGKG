# Production compatibility and presentation

Question: if analytics stop reading reconstructed and unverified activity as before, what changes for users and operators, and how is uncertain data shown without passing it off as genuine?

All figures are read-only counts from production on 2026-11-02, by provenance class (see `FINDINGS.md`). Percentages are of rows.

## 1. Why `strict` cannot be the default

`strict` includes only attested rows. Today that set is empty. Making it the default for any reader would:

| Reader | Effect of `strict` as default |
|---|---|
| Admin traffic and usage, 7-day and 30-day windows | 82 and 670 rows drop to 0 (every row in those windows is unverified) |
| Recommendations | no history for any seat; empty or non-personalised output |
| Onboarding "has this seat done X" | every seat looks as if it has done nothing; every nudge fires |

That would trade a misleading chart for a broken product. `strict` is therefore for evaluator-facing and adoption-evidence reporting only, where "no verified data" is the correct answer.

## 2. What `operational` changes

`operational` excludes `reconstructed`, `backfilled` and rule-based `not_human` rows and includes `unknown` rows, labelled.

**This table is a reference reading, not an acceptance limit.** The counts were read from production on 2026-11-02 between about 16:05 and 16:27 UTC. Each window was a trailing window measured from the moment of its own query (`now()` minus N days), so the figures moved while they were being collected (the 90-day total read 4,267 in one query and 4,263 in a later one) and they will move again with every new row and every day that passes. A later snapshot, or a moving window, can legitimately fall outside these ranges through normal activity. They illustrate the **shape** of the change (nothing in the short windows, a drop of about 91% to 96% in the long ones); they must not be used as pass or fail limits. The acceptance criterion uses fixed boundaries and is defined in "Fixed boundaries for acceptance" below.

The table nets out **all** three exclusions. Two of them are exact; the third (demo-company and administrative rows) is bounded rather than exact, because its distribution across windows was not read and no production access was made for this revision.

| Window (trailing, at the reading) | Rows at the reading | Reconstructed and back-filled removed (exact) | Left before demo/administrative rule | `operational` after that rule (range) |
|---|---:|---:|---:|---:|
| 7 days | 82 | 0 | 82 | 55 to 82 |
| 30 days | 670 | 0 | 670 | 643 to 670 |
| 90 days | about 4,263 | 1,963 (1,946 + 17) | about 2,300 | 2,273 to 2,300 |
| 180 days | 28,910 | 26,205 (26,184 + 21) | 2,705 | 2,678 to 2,687 |
| 365 days | 73,949 | 71,244 (71,223 + 21) | 2,705 | 2,678 to 2,687 |

How the last column is bounded. Among the 2,705 unmarked, non-back-filled rows, the rule-based `not_human` exclusions are the 9 rows of seats in demo companies and the 18 administrative rows (`account_created`, `team_add`, `role_add`, `role_apply`, `role_delete`, `password_reset`, not counting the 21 back-filled rows already removed). They can overlap, so between 18 and 27 rows are excluded in total (all-time, hence the 180 and 365-day ranges of 2,678 to 2,687). In a shorter window an unknown number of them, between 0 and 27 but never more than the window's rows, falls inside, which gives the wider lower bound. The 90-day base of about 2,300 is 27 pre-batch rows plus 181 plus 2,092; it drifts by a few rows with the clock.

Change at the reading: 7 and 30 days, 0 to 27 rows (up to about 33% and 4%); 90 days, about -46% to -47%; 180 days, about -91%; 365 days, about -96%.

### Prerequisite: copy equivalence (step 0 of any shadow comparison; the name is historical: what is compared is the equivalence database, never the existing staging database)

The shadow comparison is meaningful only if the equivalence copy holds the same rows and the same classification inputs as its source at the recorded cutoff. This is **verified, not assumed**. Until it passes, no shadow comparison is run and no acceptance figure is recorded.

**What the repository shows**, read from the code and not from any live copy: `ops/deploy/deploy.sh` builds the staging copy in the PostgreSQL workflow with `pg_clone_staging` (`pg_dump -Fc` piped into `pg_restore` into a `<name>_staging` database) and then sanitizes it with `ops/deploy/sanitize_staging_db.py --pg`; a separate SQLite path exists for the older engine. The PostgreSQL sanitizer purges the credential and one-time-secret tables and masks phone, e-mail, password-hash and IP columns; by its code it does not delete rows from `api_activitylog`, `api_portaluser` or `api_company`. **What the code does not show:** which path built the copy that will actually be used, whether the sanitizer ran on it, whether anything else changed its rows, and the source instant of the clone (`pg_dump` takes its own snapshot when it starts, and no fingerprint of the source is recorded). In particular, **the existing deploy path does not use an exported snapshot**, so it is not a basis for same-instant fingerprints (see Method A and Method B in step 2 of the verification). The SQLite sanitizer is not evidence about the PostgreSQL workflow, and the PostgreSQL sanitizer's code is not evidence about any particular copy. **Further facts from the repository that shape the design below** (read from `ops/deploy/deploy.sh` and `ops/docker/containers.sh`, not from any live host): (a) the existing staging database `${PG_NAME}_staging` is created `-O "$PG_USER"`, owned by the application role, and is dropped with `dropdb --if-exists --force` on every staging run, including the CI `stage` job; (b) the existing staging containers are started with `--network host`, `--env-file "$KG_BE_DIR/.env.prod"` (the production environment file) and the production warehouse directories bind-mounted without `:ro`; `deploy.sh` overrides only the database name (`-e KG_PG_NAME`) and blanks a few variables (`SENTRY_DSN`, the SMS and Turnstile keys, alert phones); (c) the application reads its database settings from `KG_PG_NAME`, `KG_PG_USER`, `KG_PG_PASSWORD`, `KG_PG_HOST`, `KG_PG_PORT` and refuses to start in production mode without `DJANGO_SECRET_KEY`.

**Separate risk, not part of this PR's remediation: staged code holds credentials capable of accessing production.** What the repository configuration indicates: `cutover_postgres.sh` requires `KG_PG_NAME/USER/PASSWORD/HOST` in `.env.prod`; production migrations run through the same helper with that file and no override, so that role can change the production database; the staging containers receive the same file with only the database name changed. So code that runs in a staging container (every commit the CI `stage` job or `deploy.sh --staging` stages, before any person promotes it) holds credentials that would let it connect to and change production if it chose to, or if the database name were not overridden. **Not verified:** the contents of `.env.prod` (it is not in the repository and was not read), whether production PostgreSQL accepts that role and password from the container's loopback address (`pg_hba.conf`), which other secrets the file holds (for example the backend `METIS_API_KEY`, which only the frontend path blanks), whether the shared `DJANGO_SECRET_KEY` makes signed values valid across staging and production, and whether the warehouse mounts are written to in practice. **Not observed:** any actual misuse or any actual connection from staging to production. The CI comment that the `stage` job "cannot reach production" is about the CI key's permitted commands, not about the code that the job stages. This is a risk for the project to assess and, if confirmed, fix in the deployment tooling; it is **not** fixed by, or copied into, the design below.

**Verification.**

1. **Identify the copy actually used**: database name, engine, build time and the commit of the deploy script that built it. A SQLite copy is not acceptable for this comparison.
2. **Take the source fingerprints at the same instant as the copy, by a method that is named, not implied.** The existing deploy path cannot do this, so the verification builds the acceptance copy by **Method B** below and records exactly which method was used.

   - **Method A, the repository's deploy path as it exists (not sufficient here).** `pg_clone_staging` in `ops/deploy/deploy.sh` is `dropdb --if-exists --force`, `createdb`, then `pg_dump -Fc "$PG_NAME" | pg_restore --no-owner --role="$PG_USER" --exit-on-error -d "$PG_STAGING"` (lines 72 to 76 at the checked commit), followed by `sanitize_staging_db.py --pg` (around line 395). It takes its own snapshot when `pg_dump` starts and **uses no exported snapshot and no held session**. Source fingerprints taken before or after it are not same-instant, so a copy built this way cannot pass the pass rule below, however the figures happen to compare. This document does not claim the deploy path does anything more.
   - **Method B, a manual, named command sequence (the one this verification requires), into a dedicated equivalence database.** The acceptance copy is **not** the existing `${PG_NAME}_staging` database: that one is owned by the application role (fact (a)), is dropped and rebuilt by every staging run, and is shared with QA and dashboards. It is a new database `<equiv-db>`, designed in the subsection "The equivalence database and the disposable application instance" below; wherever this document says "the equivalence copy" it means `<equiv-db>`. Three database roles take part, deliberately separate (authorization item 2): a **production read-only role** `<prod-read-role>`, an **equivalence administration role** `<equiv-admin-role>` that is a member of an **equivalence owner role** `<equiv-owner-role>`. The sequence, each command recorded with its exit status (`set -o pipefail`; both sides of the pipe recorded):
     ```
     # 1. name and collision checks (subsection below); any failure stops here
     # 2. open the held, read-only REPEATABLE READ exporter as <prod-read-role> (EVIDENCE_PRESERVATION.md section 4.1);
     #    inside it run the approved inventory, settings and fingerprint query files, and read T
     createdb --username=<equiv-admin-role> -O <equiv-owner-role> <equiv-db>
     # 3. isolation statements (subsection below), before any data is restored
     pg_dump  --username=<prod-read-role> -Fc --snapshot=<id> <production-db> | pg_restore --username=<equiv-admin-role> --no-owner --no-privileges --role=<equiv-owner-role> --exit-on-error -d <equiv-db> 2> <results>/restore.log
     # 4. COMMIT the exporter now: pipe exited, statuses recorded, exporter exit status 0 -- BEFORE the sanitizer
     <venv-python> -I ops/deploy/sanitize_staging_db.py --pg "dbname=<equiv-db> user=<equiv-admin-role>" --quiet
     # 5. post-restore checks (privileges, ownership) and the same approved fingerprint query files on <equiv-db>
     ```
     **Closing the exporter.** The exporter transaction is needed only until `pg_dump` has read its snapshot, which is until the pipe exits. As soon as both sides of the pipe have exited with status 0, send `COMMIT;` and `\q` to the exporter, wait for it, and require exit status 0 (as in `EVIDENCE_PRESERVATION.md` step 2), **before the sanitizer starts**; the sanitizer runs with no production transaction open, so the vacuum horizon is held back only for the dump. If the exporter ended before the pipe exited (timeout, lost connection), or its `COMMIT` is not acknowledged, the copy is treated as failed even if the pipe reported success, because the snapshot's validity is not confirmed. A failed pipe, a failed exporter or a failed sanitizer follows the failure table in the subsection below; nothing is repaired by hand. There is **no `dropdb` and no `--force`** in creation: `createdb` fails if the name exists, and an existing database is never overwritten (a retry uses a new name). Method B differs from `pg_clone_staging` in five respects: the `--snapshot` option; the explicit roles (the repository's functions use whatever connection the script runs under, and **which role that is is not shown in the repository**); an equivalence owner instead of `$PG_USER`, because membership in `$PG_USER`, which owns the production tables, would give the operator write access to production; a new database name instead of `$PG_STAGING`; and `--no-privileges`. Row data and the fingerprints do not depend on object ownership. Method B is **not in the repository**: it is an operator-run sequence, not a script, and nothing here changes `deploy.sh`. If it is later wanted as code, that is a separate, reviewed change with its own tests, outside this PR. `<production-db>` and `<equiv-db>` are different names, and the authorization names both.
   - **The exact command text and script versions are part of the authorization and of the evidence entry:** the full text of every command above with the real names filled in, the commit of `work` that the sanitizer and the deploy script were read from, and the Git blob identifiers (or SHA-256) of `ops/deploy/deploy.sh` and `ops/deploy/sanitize_staging_db.py` at that commit, so the entry shows which sanitizer ran. A command that differs from the authorized text is a different operation and needs its own authorization.
   - **Alternative path, not designed here.** The alternative to production access is a G2 amendment that extends the evidence snapshot to the seat and company tables (classification columns only) and builds the copy from that verified evidence. It is **not authorized and not designed** in this PR, for these reasons: `pg_dump --table` dumps whole tables, so it would carry the personal-data columns, and a column-limited export would be a different method that has not been designed or rehearsed; it would put decrypted copies of personal data wherever the staging copy is built, which the verification-scratch-location rules (`EVIDENCE_PRESERVATION.md` section 3) forbid unless that place also qualifies; and it needs the same encryption, custodians, retention and rehearsal as G2. Choosing it requires a new revision of these documents and a new review before any authorization.

   Record the cutoff `T` as defined below. This needs three roles in the production cluster (read-only on the production database; administration and ownership of the equivalence database only), is a separate authorization (scope, privileges, consequences and the exact commands below), is not part of PR #65, has not been requested or granted, and nothing in this document performs it.
3. **Fingerprints, by exact query files.** Non-personal, classification-relevant columns only. Each fingerprint is the output of an **approved query file** saved byte for byte by the rehearsal below, whose SHA-256 is recorded there and named in the authorization. **The same files are run, unchanged, on the source snapshot and on the staging copy**; a changed character is a different query and needs the rehearsal repeated.
   - **Files:** `fp-activitylog.sql`, `fp-portaluser.sql`, `fp-company.sql`, `fp-actions.sql`.
   - **Deterministic serialization** (the same rules as the content checksum, `EVIDENCE_PRESERVATION.md` section 4.2): `client_encoding` UTF8 and `TimeZone` UTC set identically on both sides; every value rendered with `quote_nullable(...)` (NULL differs from the empty string; quotes and backslashes are escaped); timestamps with `to_char(col, 'YYYY-MM-DD"T"HH24:MI:SS.US')`; booleans through their text form; a row string is its values joined by commas; each row string is hashed (`sha256` of its UTF-8 bytes, hex); the row hashes are joined with commas in ascending `id` order (`id` is a unique integer, so no collation is involved) and hashed again; the output is one line `count|min id|max id|hash`. `fp-actions.sql` outputs the counts by `action`, ordered by `action COLLATE "C"`, as one line, followed by the SHA-256 of that line.
   - **Content:** `api_activitylog`: `(id, user_id, action, created_at, marker present)`, where "marker present" is `(detail LIKE '%بازسازی%')::text`; `api_portaluser`: `(id, company_id, role, active, created_at)`; `api_company`: `(id, is_demo, active)`. Column names and types come from the repository's migrations for the rehearsal, and are confirmed on the source inside the exporter by a column list compared byte for byte with the approved list (as in `EVIDENCE_PRESERVATION.md` section 4.1, step 1). A difference **stops** the operation; it does not change a query.
   - **Format is validated before use:** exactly one line (`fp-actions.sql`: two), and for the four-field lines count, min and max are digits and the hash is 64 hexadecimal characters.
   - **The rehearsal must show:** equal values on a faithful restore; a different value after a one-value change in each included column, after NULL versus empty string, and after a one-microsecond change; unchanged values after the sanitizer runs on the rehearsal copy (so that the masked columns are demonstrably excluded); and the same value on repeated runs.

   The masked columns (phone, e-mail, password hash, IP) and the free text of `detail`, apart from the marker, are excluded, so masking cannot cause a false mismatch and cannot hide a real change to the inputs that drive classification.
4. **Pass rule.** Every fingerprint on the equivalence copy equals its source fingerprint. Any difference blocks the comparison until it is explained and the copy is rebuilt. There is no tolerance.
5. **After the registry migration exists**, the class counts on the equivalence copy (reconstructed rows in the registered range, back-filled rows, demo-company seats' rows, administrative actions) must equal the counts computed from the source fingerprints.
6. **Do not compare an equivalence copy with the live production table later.** Seats can be deleted (the ORM cascade removes their activity) and new rows arrive, so a later difference says nothing about the copy. Only same-instant source fingerprints count.
7. If the equivalence copy is rebuilt (always under a new database name), the verification is repeated.

The outcome (copy identity, `T`, every fingerprint pair) is recorded in the evidence entry.

**Definition of the cutoff `T`.** `T` is the value of `transaction_timestamp()` (the same as `now()` inside that transaction) of the held exporter transaction, read in that transaction with a session `TimeZone` of UTC, written to a file with `\g` like the other snapshot values, and recorded to the microsecond with its time zone. Consequences that are stated rather than assumed:

- It is the **start time of the transaction, not the instant of the snapshot**: the snapshot is taken at the first query after `BEGIN`, a moment later. `T` is therefore a window boundary, not a claim about which rows the snapshot contains.
- It does not make the window complete or clean. `created_at` may be assigned by the application server's clock, not the database's, so a row visible in the snapshot can carry a `created_at` after `T` (it is outside every window and not counted in `W`), and a row stamped before `T` may have committed after the snapshot (it is absent from the snapshot and from the copy, which is correct for both sides).
- Both sides of every comparison use the same `T` and the same snapshot, so these effects cancel; they would not cancel if `T` were taken from a different transaction, from `now()` at query time, or from the clone's finishing time, so none of those is allowed.
- `T` is a recorded input of the evidence entry; when the copy is refreshed, a new `T` is taken in a new exporter transaction.

**Scope and prerequisites of the separate production-read authorization.** Reading production for the copy-equivalence check is a different act from the evidence preservation (G2) and from the review of this PR (G1); an approval of either does not cover it. It is requested in GitHub #64 by the product owner, as a single-use authorization, and states all of:

1. **What is read and written:** (a) the read-only exporter transaction and the dump of the **whole production database** (personal data is read), and the approved non-personal fingerprint query files; (b) in the **same PostgreSQL cluster**, creating one **new** database `<equiv-db>` (never dropping or overwriting an existing one), restoring into it, sanitizing it, and, at the end, dropping it; (c) the cluster-level changes listed in item 11, and no others. No write to any production database object, no migration, no change to production data, and no change to any backup. Production, staging and equivalence database names differ, and all three are named.
2. **Roles and privileges: three, separate.** A named operator; connection details outside the repository; no credentials in commands, logs or the evidence entry. Each role has its own password, generated for this purpose and kept outside the repository in a `0600` file; none is the production application password. The roles are created with `VALID UNTIL` set to the deletion date plus one day, and are disabled or dropped after use, including after a failure (the subsection "Results, removal and temporary credentials").
   - `<prod-read-role>`: login role; not a superuser; no CREATEDB, CREATEROLE, REPLICATION or BYPASSRLS; read access only, for example membership in the predefined role `pg_read_all_data` (PostgreSQL 14 and later); no write privileges anywhere; no membership in any other role. Verified before use by catalog queries (attributes, memberships, privilege checks on the production tables), and recorded. **Unverified:** that this is enough for `pg_dump` of the whole database (for example large objects, or objects that need other privileges); the rehearsal must show `pg_dump` runs with exactly this role and nothing more, and the authorization is not requested until it has.
   - `<equiv-admin-role>`: login role with CREATEDB; a member of `<equiv-owner-role>` and of nothing else; not a superuser; **no privileges on any production object** beyond the default public ones (verified by privilege checks on the production tables, recorded).
   - `<equiv-owner-role>`: login role; owner of `<equiv-db>` only; the role the disposable application instance connects as; no privileges on production.
   - **Why not the application role:** `createdb -O` and `pg_restore --role` require membership in the target owner role (or a superuser). Membership in `$PG_USER`, which owns the production tables, would give the operator write access to production; a superuser cannot be bounded. Neither is used.
   - **Unverified assumptions:** whether these roles exist; under which role `deploy.sh` runs; whether a database owner's role member may drop the database (expected from the documentation of `DROP DATABASE`, to be shown by the rehearsal); and whether the cluster's `pg_hba.conf` already allows these roles to connect over the loopback TCP address the containers use. Creating the roles is a write to the cluster's catalogs, and any change to `pg_hba.conf` is a change to cluster configuration: both need their own explicit entries in item 11, and without them Method B is unavailable and the check is not run.
3. **Window and freeze.** A stated off-peak window for the creation (exporter, dump, restore, sanitizer, fingerprints), with a maximum life for the exporter transaction (the 15-minute idle timeout is a ceiling, section 4.1 of `EVIDENCE_PRESERVATION.md`), and a **freeze for that window**: no deploy (`deploy.sh`, `kgkg-promote`; a push or merge to `work` starts the CI `stage` job, which is a deploy-like run), no migration on production, and no scheduled job that dumps or rebuilds databases. The freeze does not need to cover the later life of `<equiv-db>`: no repository workflow touches that name (the staging runs touch `$PG_STAGING` only), and its removal uses no `--force`.
4. **Destination:** `<equiv-db>`, named in advance (rules in the subsection below), on a host and with access control approved for **unsanitized personal data for the time between restore and sanitization**, and for sanitized-but-still-personal data (usernames, display names and activity remain after sanitizing) for its whole life; nobody queries the copy before the sanitizer has run and its result is checked.
5. **Method and versions:** Method B as written in step 2, with the exact command text (real names filled in), the commit of `work` and the blob identifiers or SHA-256 of `ops/deploy/deploy.sh` and `ops/deploy/sanitize_staging_db.py` that the commands mirror and the sanitizer run uses, all recorded in the authorization, together with the approved fingerprint query files and their SHA-256 (step 3). Neither script is changed for this purpose, and the operation is **not** the unmodified deploy path.
6. **Capacity:** free space on the destination and on the production host for the transaction's side effects, read at execution time.
7. **Prerequisites met first:** the rehearsal of the snapshot method on a non-production database (`EVIDENCE_PRESERVATION.md` section 4.1) and **the rehearsal of Method B and of the fingerprint query files (below)** have passed, with their records and the SHA-256 of each approved query file attached; the roles of item 2 exist and are verified; the equivalence database is not shared with other work.
8. **Stop conditions:** any error, a failed name or collision check, a failed privilege or isolation check, a column list that differs from the approved one, a fingerprint mismatch, an unexpected write or a lock wait on production, a failed side of the pipe, insufficient free space, or the window closing ends the operation; a half-built `<equiv-db>` is dropped (without `--force`) and not used; it is repeated only under a new authorization.
9. **Afterwards:** the exporter transaction is committed or rolled back and confirmed gone, temporary files are removed, the outcome (copy identity, `T`, every fingerprint pair, pass or fail) is recorded, and the authorization lapses.
10. **Consequences accepted explicitly, because the equivalence database shares the cluster with production:**
    - **Locks.** The whole-database `pg_dump` holds ACCESS SHARE locks on every table for its duration. That does not block ordinary reads and writes, but a statement that needs ACCESS EXCLUSIVE (many `ALTER TABLE` forms, `DROP`, `TRUNCATE`, some migrations) waits for it, and ordinary queries that arrive after the waiting statement queue behind it. This is why migrations and deploys are frozen (item 3) and why an unexpected lock wait is a stop condition. The rehearsal observes it.
    - **Vacuum.** The held transaction holds back cleanup of dead rows in the whole cluster for its life.
    - **Temporary unsanitized data.** From the end of the restore until the sanitizer has finished, `<equiv-db>` holds unsanitized personal data, credential tables and secrets inside the production cluster, visible to anyone with access to the cluster. Sanitizing deletes or masks rows but does not erase the earlier bytes: they remain in WAL, in dead tuples and free space until vacuum and reuse, and in any cluster-level or physical backup, WAL archive or replica taken in that period. The repository's own backups are per-database (`pg_dump -Fc "$PG_NAME"` in `deploy.sh`, `pg_backup`) and do not include the staging database; whether any cluster-level backup, WAL archive or replica exists is **not shown in the repository** and must be established and named in the authorization, with their retention. Dropping the staging database later does not remove WAL or backups.
    - **Exposure outside the database.** Unsanitized values can reach the server log, error `DETAIL` lines, `pg_stat_activity`, `pg_stat_statements`, `auto_explain`, any log shipper or monitoring role, the tools' stderr, container logs, WAL, archives and replicas (the subsection above lists the channels). The live settings are not known; they are read by the pre-flight, and **the authorization names every channel that is on, its retention and readers, and accepts or rejects it in writing**; an unlisted or unknown channel is a stop condition.
    - **Disk and WAL volume.** A second copy of the database, its sanitization (which rewrites rows) and the WAL that all of it generates, on the data and the WAL volumes. The size of the production database is not stated in the repository: it is read at execution time (`pg_database_size`), and the operation stops unless free space on each volume is at least three times that size (an assumption to be checked by the rehearsal, which records the actual peak).
    - **No forced disconnections of other users.** Nothing else connects to `<equiv-db>`, and it is removed with plain `dropdb` (no `--force`), which fails while a session is connected: the disposable instance is stopped first. The existing staging containers and QA are untouched.
    - **Lifetime.** The owner of `<equiv-db>` and its deletion date are named in the authorization (default at most 7 days, because the shadow comparison is run once; an extension is a recorded decision), and the removal steps below are executed and recorded.
11. **Exact commands and application configuration, and cluster-level changes.** The authorization contains, with the real names filled in: the commands of Method B; the name and collision checks, the isolation statements, the restore flags, the removal and credential-disabling commands and the instance's `docker run` command, environment file and **variable-by-variable decision table** as written in the subsection below; the approved query files (the four fingerprints, `inventory.sql`, `settings.sql`, `replication.sql`) with their SHA-256; the accepted channels of the previous item; the **cluster administrator** who will disable or drop the roles and remove any `pg_hba.conf` change, and when; and the complete list of cluster-level changes it permits: creating `<prod-read-role>`, `<equiv-admin-role>` and `<equiv-owner-role>` with `VALID UNTIL` and their memberships (only if they do not exist), any `pg_hba.conf` change (only if needed), and creating, restricting and dropping `<equiv-db>`. A command that differs from the authorized text is a different operation and needs its own authorization.

Without this authorization, the copy-equivalence prerequisite stays **unverified** and no shadow comparison is run. The alternative path in step 2 is not an authorization route today: it is undesigned and needs a revision and a review first.

### The equivalence database and the disposable application instance (design, not executed)

**Why a dedicated database.** The existing staging database is owned by the application role, is dropped and rebuilt by every staging run, and is used by other work; Method B cannot drop it without the very membership it must avoid, and must not disturb it. A new database with its own owner needs no `--force`, cannot collide with a staging run, and can be removed without touching anything else.

**Name and collision checks** (before anything is created; any failure stops the operation):
```
PG_NAME=<production-db>; PG_STAGING=${PG_NAME}_staging
EQUIV=<equiv-db>                                                   # form: ${PG_NAME}_equiv_YYYYMMDD_N, N = 1, 2 or 3 (one per attempt)
case "$EQUIV" in "${PG_NAME}_equiv_"[0-9][0-9][0-9][0-9][0-9][0-9][0-9][0-9]_[1-3]) ;; *) echo "bad name"; exit 1;; esac
[ "$EQUIV" != "$PG_NAME" ] && [ "$EQUIV" != "$PG_STAGING" ]
test "$(psql --username=<equiv-admin-role> -d postgres -Atc "SELECT count(*) FROM pg_database WHERE datname = '$EQUIV'")" = 0
test "$(psql --username=<equiv-admin-role> -d postgres -Atc "SELECT count(*) FROM pg_database WHERE datname LIKE '${PG_NAME}\_equiv\_%'")" = 0   # no leftover from an earlier attempt
docker ps -a --filter name=kgkg-equiv-backend --format '{{.Names}}' | grep -q . && exit 1     # container name unused
ss -ltn "sport = :<equiv-port>" | grep -q LISTEN && exit 1                                   # loopback port unused (not 8000, 3000, 8110, 3107)
test ! -e /opt/KGKG_equiv/<date>                                                              # instance directory unused
umask 077; mkdir -p /opt/KGKG_equiv/<date>/{results,data,logs,spool,equivcfg}               # only after every check above passed; <results> = /opt/KGKG_equiv/<date>/results
```

The repository's other scratch database, `kgkg_restore_test` (`ops/observability/verify_restore.py`, which runs `dropdb --if-exists --force` and `createdb` without a role option), has a different name; its schedule is not shown in the repository and is checked against the freeze window.

**Pre-flight, read-only, inside the exporter, before anything is created.** Three approved query files, treated exactly like the fingerprint files (saved byte for byte by the rehearsal, hash recorded, named in the authorization, output saved to the `0700` results directory and format-checked):
- `inventory.sql`: what the whole-database dump will contain, so that the live object inventory and privileges are **read, not assumed**: installed extensions; the number of large objects; event triggers; publications and subscriptions; foreign servers; non-default ACLs on schemas, tables and sequences (`relacl`, `nspacl` not null) and `pg_default_acl` rows; the roles that own objects or appear in ACLs; schemas; and the table and total database sizes.
- `settings.sql`: the server settings that decide where unsanitized values can go (next paragraph).
- `replication.sql`: `pg_stat_replication` and `pg_replication_slots` row counts.

Any class of object, ACL or setting that the rehearsal did not exercise **stops** the operation (it is not improvised around). Settings or objects that `<prod-read-role>` cannot see are recorded as **unknown**, not assumed to be safe.

**Creation, isolation and restored privileges.** Run by `<equiv-admin-role>` right after `createdb`, on the new database only:
```
REVOKE CONNECT ON DATABASE "<equiv-db>" FROM PUBLIC;
GRANT  CONNECT ON DATABASE "<equiv-db>" TO <equiv-owner-role>;
```
A new database grants `CONNECT` to everyone by default, so the revoke keeps other roles, including the production application role, out of it. The statements touch only `<equiv-db>`. Nobody else connects, and no instance runs, until the sanitizer has finished and its result is checked. The restore uses `--no-owner --role=<equiv-owner-role>` (every restored object is owned by the equivalence owner, not by the production owner) and **`--no-privileges`** (the dump's `GRANT` and `REVOKE` commands, which could name the production application role or other production roles, are not replayed; the repository's own `verify_restore.py` also restores with `--no-privileges`). Whether `--no-privileges` also drops default-ACL entries in the way the documentation describes is **not assumed**; after the restore the operator checks, and records, that no object in `<equiv-db>` has an ACL entry for any role other than the equivalence roles (the same catalog queries as in `inventory.sql`, run on `<equiv-db>`), that every object is owned by `<equiv-owner-role>`, and that `<equiv-owner-role>` and `<equiv-admin-role>` have no `SELECT` on any production table and the production application role cannot connect to `<equiv-db>`. A mismatch stops the operation. **Extensions and ownership:** the restore runs as a non-superuser, so `CREATE EXTENSION` and `COMMENT ON EXTENSION` succeed only for trusted extensions owned by the creating role. The repository contains `CREATE EXTENSION IF NOT EXISTS pg_trgm` (`KG_backend/api/cardb_pg.py`), but it is **not established** which database that runs in or what the live inventory is. With `--exit-on-error` an extension that cannot be created fails the restore loudly (it is not skipped), and the rehearsal must restore a database that contains each extension class the pre-flight can report.

**Exposure of unsanitized values outside the database.** Between the restore and the end of the sanitizer, and in any error path, real values can be written outside `<equiv-db>`, and sanitizing (which deletes and updates rows) does not remove what was already written. The channels, none of which the repository shows the live settings of:
- the PostgreSQL server log: statement logging (`log_statement`, `log_min_duration_statement`), error statements (`log_min_error_statement`), error verbosity, and the logging of parameters (`log_parameter_max_length`, `log_parameter_max_length_on_error`); an error such as a duplicate key or a failed restore step carries a `DETAIL` or `Command was:` line with row values;
- what the cluster loads or exposes: `pg_stat_activity` query text, `pg_stat_statements`, `auto_explain` (`shared_preload_libraries`), and anything that tails or ships the server log or the container logs (a log shipper, a monitoring role);
- the tools' own output: `pg_restore` and the sanitizer's stderr, `psql` output, shell history, and the disposable instance's container and application logs;
- WAL, archives, replicas and slots (`archive_mode`, `archive_command`, `wal_level`, `max_wal_senders`, `max_replication_slots`, `listen_addresses`), which carry the pre-sanitization bytes wherever they are sent.
`settings.sql` reads these with `pg_settings` as `<prod-read-role>`; the result is recorded, and **the authorization lists every channel that is on, its retention and who can read it, and accepts or rejects each in writing**; an unlisted or unknown channel is a stop condition, not an assumption. Error output of the tools is written to files in the `0700` results directory and is not pasted into chat, tickets or the evidence entry; only the status and a hash are reported. The repository shows no PostgreSQL exporter or log shipper in `ops/observability` (only `bizsnap.py` and `verify_restore.py` use the database), which is not evidence about the live host.

Configuration rules: no production environment file, no production secret, no production warehouse mount (if the analytics under comparison need warehouse files, a **read-only** mount is the only permitted exception and is named in the authorization), no served hostjobs spool, no nginx route; it listens on loopback only and the operator reaches it from the host (or by SSH port forwarding); it is not restarted automatically. **Root and host networking: what they mean here.** The backend image sets no `USER`, so the process runs as root inside the container; `--network host` (the repository's own choice for all its containers) puts it in the host's network namespace, so it can open connections to every loopback and host service: the production PostgreSQL port, other local services, and the Chrome debugging port 127.0.0.1:9222 that `containers.sh` documents for the TIS crawler panel if that browser is running. `--cap-drop ALL` and `no-new-privileges` remove kernel capabilities and privilege gain, but not the network reach, and a writable bind mount is written as root. What keeps the instance away from production is therefore **only** the equivalence role's lack of privileges (and `pg_hba.conf`), not the network, which is why the privilege checks are mandatory. A bridge network would need the cluster to listen on a non-loopback address, a configuration change that is not proposed. Hardening that is **not assumed to work** and is rehearsed: `--user <uid>:<gid>` with the instance directories owned by that uid (the image may need root), `--read-only` with writable mounts only for the data, log and spool directories, and `--pids-limit` and memory limits. The operator running Docker (root on the host today) is outside this isolation.

**Assumptions that stay unverified until rehearsed:** that `-e` and `--env-file` precedence and the environment above are enough for the settings to start; that the image starts and passes its health check without the warehouses and the model cache; that `--cap-drop ALL`, `no-new-privileges` and a non-root user do not stop it; that no host daemon serves the instance's spool; and that `pg_hba.conf` accepts the roles.

**Failure paths and cleanup.** Each row ends in the same safe state: the container is stopped and removed, no unsanitized database is left connectable or queried, the temporary credentials are disabled, and what happened is recorded. `<equiv-db>` is dropped with plain `dropdb` (never `--force`); if sessions block it, the operator identifies and stops their owners and tries again.

| Event | Action |
|---|---|
| a name, collision, pre-flight or stop-rule check fails | stop; nothing was created; fix and start again with a new attempt number |
| `createdb` or the isolation statements fail | stop; if the database exists it is empty: drop it; record |
| the pipe fails on either side, or `pg_restore` reports an error | send `ROLLBACK;` to the exporter if it is still open; drop the half-built `<equiv-db>`; `restore.log` (sensitive) stays in the `0700` results directory until the removal steps, and is then deleted unless the authorization says to keep it encrypted; do not start the sanitizer or an instance; a retry uses the next attempt number |
| the exporter ended before the pipe exited, its exit status is not 0, or its `COMMIT` is not acknowledged | treat the copy as failed even if the pipe succeeded; drop it; retry with the next attempt number |
| the sanitizer fails or its result check fails | `<equiv-db>` holds unsanitized values: **drop it immediately**, never repair or query it, and record; if the drop fails, `CONNECT` stays revoked, the operator escalates, and no instance is started |
| the post-restore privilege, ownership or ACL check fails | stop; drop the database; the failed attempt is recorded |
| a fingerprint on `<equiv-db>` differs from its source fingerprint | no tolerance: no instance is started; drop the database; explain before any rebuild |
| the instance fails to start or become healthy | stop and remove the container; keep `<equiv-db>` only until the removal steps below; its container log (sensitive) is handled the same way |
| the operator's session is lost, or the host restarts, during an attempt | the exporter dies with its connection; the next person lists databases matching `${PG_NAME}_equiv_%` and containers named `kgkg-equiv-*`; anything not recorded as complete is removed by the steps above before a new attempt |
| three attempts fail | stop and escalate to the product owner; do not improvise a different method |
| a removal step fails | continue with the credential-disabling step (below) anyway; leave `CONNECT` revoked; record exactly what remains and escalate |

**Results, removal and temporary credentials, in this order** (each step checks the previous; failure paths above use the same order):
1. Stop the instance: `docker rm -f kgkg-equiv-backend`. Nothing is connected afterwards.
2. **Save and verify the comparison outputs before anything is deleted.** The results are the files in `/opt/KGKG_equiv/<date>/results/`: the fingerprint outputs on both sides, the pre-flight, privilege and ACL checks, the command log with every exit status, the comparison outputs for each window, and `results.sha256` listing each file. They contain counts, hashes and identifiers, not personal data. Copy them to the approved location, recompute `sha256sum` there, and compare with `results.sha256` and with the independently recorded values in the evidence entry. If any hash differs, the copy is repeated; until it succeeds, or the product owner records a decision, the `results` directory alone is kept (mode `0700`). **Steps 3, 4 and 6 are never skipped because of this**: the password files are deleted, the database is dropped (the comparison can be repeated under a new authorization; a copy of personal data is not kept to protect an unsaved result) and the credentials are disabled. The instance and tool logs (request paths, usernames, error details) are **not** results: they are kept only if the authorization says so, encrypted like the other logs, and otherwise deleted with the directory.
3. Delete the password files first: `rm -f /opt/KGKG_equiv/<date>/equiv.env` and any file holding a role password.
4. Drop the database: `dropdb --username=<equiv-admin-role> <equiv-db>` (no `--force`; it fails while anyone is connected).
5. Remove the directory: `rm -rf /opt/KGKG_equiv/<date>` (file deletion does not guarantee the bytes are gone on journaling or copy-on-write filesystems; the limit is recorded).
6. **Temporary credentials.** The roles are created with a password validity limit, `VALID UNTIL '<deletion date plus one day>'`, so that password login stops by itself even if every step above is skipped (the setting applies to password authentication; it is not assumed to affect other authentication methods, which the rehearsal and the host check cover). In addition, and by the cluster administrator named in authorization item 11 (the equivalence roles cannot do it: they have no `CREATEROLE`), **after step 4 or after any failure path**: `ALTER ROLE <equiv-admin-role> NOLOGIN PASSWORD NULL`, the same for `<equiv-owner-role>`, and, unless the authorization keeps the roles for a later check, `DROP ROLE` for the equivalence roles. `<prod-read-role>` is disabled the same way. A password is used for one operation and never reused. Any `pg_hba.conf` line added for these roles is removed.
7. Confirm, and record: no container named `kgkg-equiv-*`; no database matching `${PG_NAME}_equiv_%` in `pg_database`; no directory `/opt/KGKG_equiv/<date>`; the roles are `NOLOGIN` or gone and their passwords null; no `pg_hba.conf` change remains. The backend **image is not removed** (it belongs to the release pipeline). None of this removes WAL, archives, replicas, backups or logs that received values earlier.

**Capacity** is read at execution time (item 10 of the authorization). **Sensitive data**: `<equiv-db>` holds real customers' data (sanitized of credentials and masked contact details, but display names, usernames, company data and activity remain); access is limited to the operator, the instance is loopback-only, nothing is exported from it except the non-personal fingerprint and comparison outputs, and its logs stay inside the `0700` directory until removal.

**Not established, listed so that nobody assumes it:** `pg_dump` privileges for `<prod-read-role>`; the availability of the roles; whether `pg_hba.conf` already permits them; the live object inventory and ACLs; the server's logging, statistics and preload settings; whether the cluster archives WAL, has replicas, slots or takes cluster-level or physical backups (the repository shows only per-database `pg_dump -Fc "$PG_NAME"` backups, which do not include `<equiv-db>`); the production database's size; the host's free space; and whether anything else on the host reads the PostgreSQL log or the container logs.

### Rehearsal of Method B, the equivalence database and the fingerprint queries (required before the authorization is requested; not executed)

Nothing here has been run. It is done on a **non-production** PostgreSQL 16 cluster, in the same kind of shell (bash, Ubuntu 24) as the production host, with synthetic data, the repository's own `sanitize_staging_db.py --pg` at the commit named in the authorization, and an image built by the repository's pipeline. A failed item is a finding. The record, with the SHA-256 of each approved query file (fingerprints, `inventory.sql`, `settings.sql`, `replication.sql`), the exact command texts, the environment table and file's variable names and the `docker run` command, is attached to the authorization request, and **no production read is requested before it exists**. Because the live inventory, privileges and settings are not known, the rehearsal cluster is built to contain the **classes** the pre-flight can report (not a copy of production), and an unexercised class is a stop rule in the real run.

1. **Roles and `pg_dump` privileges.** The three roles of authorization item 2 are created with `VALID UNTIL`. `pg_dump` runs as `<prod-read-role>` with the proposed privileges and nothing more, against a database that has a large object, a sequence, an extension, event trigger and publication-like objects, non-default ACLs and default ACLs; that role cannot write; `<equiv-admin-role>` can neither read nor write the rehearsal "production" tables; `createdb -O`, `pg_restore --role` and plain `dropdb` by a member of the owner role work as written; membership in the application role is shown to give write access to the rehearsal "production" tables (the reason for not using it).
2. **Name and collision checks.** Each check stops the operation on a bad name, an existing database, a leftover database of the equivalence form, an existing container, a busy port and an existing directory. `createdb` fails on an existing name and nothing is overwritten.
3. **Pre-flight files.** `inventory.sql`, `settings.sql` and `replication.sql` run as `<prod-read-role>`, their outputs pass the format checks, a setting or object that role cannot see is recorded as unknown, and each stop rule (an unexercised object class, a logging, preload, archiving or replication setting that the authorization has not accepted) triggers when the rehearsal cluster is configured to trigger it.
4. **Pipeline and exporter closing.** With `set -o pipefail`, `COMMIT` of the exporter after the pipe and **before** the sanitizer; the backend of the exporter is observed not to hold a snapshot (no `backend_xmin`) while the sanitizer runs. Failure injection, each followed by the matching row of the failure table: kill `pg_dump`; kill `pg_restore`; make the restore fail on a duplicate key; end the exporter before the pipe exits (short idle timeout) while the pipe still succeeds; withhold the exporter's `COMMIT`. In every case the half-built database is dropped with plain `dropdb`, nothing is repaired by hand, and with the exporter held, concurrent writes do not appear in the copy.
5. **Restored privileges, ownership and extensions.** With `--no-privileges --no-owner --role=<equiv-owner-role>`: no ACL entry for a "production" role remains (and whether default ACLs are replayed is observed and recorded, not assumed); every object is owned by the equivalence owner; a trusted extension (such as `pg_trgm`) restores as a non-superuser; an extension that needs a superuser fails the restore loudly under `--exit-on-error`; a large object, an event trigger and a publication behave as recorded.
6. **Isolation.** After the `REVOKE`/`GRANT`, the rehearsal "application" role cannot connect to `<equiv-db>`; the equivalence roles have no `SELECT` on any rehearsal "production" table; connections over loopback TCP as each role succeed or fail as the `pg_hba` assumption says.
7. **Sanitizer and its failure path.** `sanitize_staging_db.py --pg` runs on the restored copy as `<equiv-admin-role>`; its result is checked; an injected sanitizer failure leads to an immediate plain `dropdb`; the copy is not queried before the sanitizer has finished.
8. **Fingerprints.** The four fingerprint query files give equal values on the source snapshot and on the sanitized copy; the detection tests of step 3 pass; the format checks pass and fail on the negative controls; fingerprints are taken before any instance starts.
9. **Exposure of values outside the database.** The rehearsal cluster is deliberately configured verbosely (`log_statement = all`, parameter logging, `log_min_error_statement`, `pg_stat_statements`, `auto_explain`, a log tail standing in for a shipper). The restore, the sanitizer and the injected errors of items 4 and 7 are run, and the report records **where** synthetic marker values appear: the server log, `pg_stat_activity`, `pg_stat_statements`, the tools' stderr files, the container logs and WAL. It also shows that the stop rule fires on those settings, and that the error files are written only to the `0700` directory.
10. **Disposable instance and environment decisions.** The environment table and `docker run` command are used exactly as written. The container starts and passes its health check; `docker inspect` shows no production variable, secret or mount; `-e`/`--env-file` precedence is as assumed; a connection attempt by the instance's role to the rehearsal "production" database is refused; the effect of **unsetting** `KG_HOSTJOBS_DIR` is observed in a throwaway container (helpers acting locally), and with it set and an empty, unserved spool a host-job request is queued and never executed; a feedback write lands in `/data/equiv/feedback.db`; the image runs without the warehouses and the model cache, or the minimal read-only exception is recorded; the analytics under comparison do not need retrieval or an embedding model, or that is recorded as a finding; any further variable that `settings.py` demands is recorded without a production secret. ### Fixed boundaries for acceptance

Acceptance is evaluated on one **equivalence snapshot** that has passed the prerequisite above, with the snapshot and the windows fixed in advance, so that normal activity cannot move the result.

1. **One fixed cutoff `T`**: the cutoff defined above (the `transaction_timestamp()` of the exporter transaction that the copy was made from), recorded by the staging-equivalence verification. Every count uses the explicit window `created_at >= T - N days AND created_at <= T`, for N in 7, 30, 90, 180 and 365. No query in the shadow comparison uses `now()`.
2. **Both code paths are evaluated at `T`.** The old behaviour and the new `operational` behaviour are run with the analytics code's `as_of` input set to `T` (the design adds an `as_of` parameter, default the current time, so the comparison is reproducible).
3. **The bounds are recomputed from that snapshot**, not copied from this document. For each window, from the equivalence copy: `W` all rows, `R` reconstructed, `B` back-filled, `D` rows of demo-company seats and `A` administrative rows, each counted only if not already in `R` or `B`, and `O` rows in both `D` and `A`.
4. **Bounds:** `W - R - B - (D + A) <= operational <= W - R - B - max(D, A)`. Once `O` is read the value is exact: `operational = W - R - B - (D + A - O)`.
5. **Pass criterion:** for every window, the measured `operational` count equals `W - R - B - (D + A - O)` computed by a separate query from the same snapshot (exact equality), and lies inside the bounds in step 4. The recorded `T`, the six counts per window and the measured values go into the evidence entry. Nothing is compared with the 2026-11-02 reference table.
6. **If the equivalence copy is rebuilt**, `T` and every figure are recomputed; the previous result is not reused.

Consequences to plan for:

- **Wide-window charts fall off a cliff.** On the 2026-11-02 reading, a 365-day engagement chart goes from 73,949 rows to between 2,678 and 2,687. Without annotation this reads as a collapse in usage. Each affected view needs a visible note: "N reconstructed rows are excluded; history before 2026-07-04 has no application data."
- **Feature discovery.** Seats with any manual view: 26 including reconstructed rows, 12 without. 14 seats would flip from "has read the manuals" to "has not", and their nudges would start to fire. That is the correct behaviour and it will look like a sudden change in onboarding traffic.
- **Recommendations.** Peer history shrinks from 71,888 to at most 1,354 manual views from 12 seats (fewer by any made by demo-company seats). Seats with no recent history fall back to non-personalised suggestions; this fallback must be tested (it is part of `TEST_PLAN.md`).
- **Operators.** Reads only; no write path changes. A search of `ops/` found no alert, watchdog, exporter or dashboard that reads `api_activitylog`; the only references are the staging sanitizer and the restore verifier. Anything outside the repository was not searched. Disk, locks and migrations are unaffected (nullable column, no rewrite).
- **Concentrated use.** In the last 30 days five seats produced all activity and the top-manager role accounts for 302 of 670 rows. Dashboards built on such a small base will be volatile; the note on small samples belongs in the UI.

## 3. Presentation

Never one unlabelled number called "genuine".

| Element | Behaviour |
|---|---|
| Headline KPI | "n unverified application events (excluding m reconstructed)", with "verified: v" beside it, v being 0 until attestations exist |
| Charts | stacked series: verified, unverified; excluded classes shown as a separate, muted line or a footnote count, never summed in |
| Tables | a class column in the admin audit view; filter by class |
| API | additive `provenance` object: `mode`, `included` classes, `counts` per class, `excluded` per class; existing keys unchanged |
| Wide windows | banner when the window reaches back into a registered range |
| Evaluator exports | `strict` only; states the attested scope and "no verified data" when empty |
| Small samples | "based on n events from k seats" when k is under 10 |

## 4. Per-reader policy

| Reader | Mode | Notes |
|---|---|---|
| `adminops` traffic, today and recent feeds | operational | composition shown |
| `portal` usage report | operational | composition and wide-window banner |
| `insights` funnel | operational for activity; `dormant_accounts` unchanged (reads `last_login_at`) | do not back-fill `last_login_at` |

## 5. Rollout

1. Implement behind a flag per reader (`KG_ACTIVITY_PROVENANCE_<READER>`), default off.
2. **Shadow mode** on the disposable equivalence instance (never on the existing staging stack), only after the copy-equivalence prerequisite (section 2) has passed for that copy: compute old and new values, log the difference, show nothing new.
3. **Recompute and compare on the fixed equivalence snapshot**, as defined in "Fixed boundaries for acceptance" (section 2): use the recorded cutoff `T` and windows `[T - N days, T]` for 7, 30, 90, 180 and 365 days, recompute `W`, `R`, `B`, `D`, `A` and `O` from that snapshot, and compare each dashboard's measured `operational` count with `W - R - B - (D + A - O)`. The 2026-11-02 reference table is not used for this comparison.
4. Enable readers one at a time; each with its annotation and its test.
5. Production promotion only by a person (`kgkg-promote <sha>`).
6. Rollback is the previous image tag plus turning the flag off; no data to restore.

## 6. What has not been assessed

User-visible impact on customers' own dashboards if any are exposed outside the admin and team roles; this must be checked reader by reader during step 2 of the rollout. The count of Grafana or other external dashboards reading the table directly is not known (none was found in the repository).
