# Remediation design: provenance- and attribution-aware activity analytics

Status: **proposal for review (revised after review of PR #65).** No code, migration or production change exists. Nothing here may be deployed or run against production without passing the gates in section 9. Companion documents: `ATTESTATION_POLICY.md`, `COMPATIBILITY_ASSESSMENT.md`, `TEST_PLAN.md`.

## 1. Goals and non-goals

Goals: keep every row; make provenance **and** attribution explicit and separate; make normal analytics, onboarding and recommendations use only appropriate activity; keep full, unfiltered access for authorized audit; do it in one place, with tests that stop regression.

Non-goals: deleting, updating or anonymizing any existing `api_activitylog` row; deciding whether the reconstructed rows are eventually removed (section 10); changing how seats are deleted (explicitly **out of scope**, see 7.6).

## 2. Classification model: two separate axes

An earlier draft used a single class (`verified_genuine`). That conflated two different facts and is withdrawn. Evidence that a record **existed** before the reconstruction batch is not evidence that it records **real human work**, and a technical origin of `origin='app'` says only that application code wrote the row. Demo accounts, scripted checks, QA runs and administrative operations are all written by application code too.

### 2.1 Provenance axis (technical, objective)

| Value | Meaning | Rows today |
|---|---|---:|
| `reconstructed` | generated by the reconstruction batch | 83,486 |
| `backfilled` | created from account state with a historical timestamp | 21 |
| `app_preexisting` | application write that appears in an independent backup older than the batch | 432 |
| `app_unconfirmed` | application write with no independent source | 2,273 (181 before the batch, 2,092 after) |
| `app` | application write made after the provenance layer is deployed (`origin='app'`) | none yet |

### 2.2 Attribution axis (behavioural)

| Value | Meaning | How it is assigned |
|---|---|---|
| `not_human` | synthetic, demo, test, QA, scripted or administrative | by rule, immediately (below), or by attestation |
| `unknown` | no basis either way | the default for everything else |
| `human_confirmed` | attested as real work by a real person | only by attestation meeting `ATTESTATION_POLICY.md` |

Rule-based `not_human` (objective, applied automatically, can only be undone by an attestation):

- every `reconstructed` or `backfilled` row;
- every row of a seat whose company has `is_demo = true`;
- administrative actions: `account_created`, `team_add`, `role_add`, `role_apply`, `role_delete`, `password_reset` (39 unmarked rows today);
- rows of seats recorded in the seat-kind registry as `demo`, `test`, `qa` or `admin_ops`.

`app` and `app_preexisting` never imply `human_confirmed`. A new row defaults to `unknown` attribution.

### 2.3 Metric modes

| Mode | Includes | Used for |
|---|---|---|
| `strict` | provenance `app*` and attribution `human_confirmed` | anything published to evaluators or used as evidence of adoption |
| `operational` | provenance `app*` and attribution not `not_human` (so `unknown` is included, always labelled) | dashboards, onboarding state, recommendations |
| `audit` | everything, both axes visible | audit, Django admin, evidence tooling |

Today `strict` is empty: no row has been attested. That is the honest state, and it is why `strict` is not a default for anything operational (see `COMPATIBILITY_ASSESSMENT.md`).

## 3. Data model (all additive)

### 3.1 `api_activityprovenance` (new, append-only)

| Column | Notes |
|---|---|
| `id` | primary key |
| `dimension` | `provenance` or `attribution` |
| `value` | a value from section 2 |
| `id_min`, `id_max` | inclusive range of `api_activitylog.id`; `id_min <= id_max` |
| `seat_ids` | optional integer array: restricts the entry to these seats (cohort scope) |
| `actions` | optional text array: restricts the entry to these actions |
| `created_from`, `created_to` | optional time bounds on `created_at` |
| `marker` | optional substring of `detail` |
| `basis` | short code: `rule`, `generator_manifest`, `backup_match`, `audit_log_match`, `seat_attestation`, `sample_attestation`, `event_match` |
| `evidence_ref` | pointer to a document, checksum entry or restore-verified artifact; never data |
| `analyst`, `approver` | two different people for any change to `human_confirmed` |
| `rows_recorded` | rows covered **at the time of recording** (immutable fact; e.g. 102,054 for the batch); nullable |
| `recorded_at`, `review_by` | when, and the date by which the entry must be re-confirmed |
| `supersedes_id` | a change adds a new row pointing at the one it replaces |

Surviving-row counts are **not stored**: they change when a seat is deleted, so a stored value would be stale or silently wrong. They are computed on demand by a diagnostic query and compared with `rows_recorded` in a test.

### 3.2 `api_seatkind` (new, append-only)

`seat_id`, `kind` (`person`, `demo`, `test`, `qa`, `admin_ops`, `unknown`), `evidence_ref`, `recorded_by`, `recorded_at`, `supersedes_id`. A seat has no foreign key to the activity table, and the registry does not use a foreign key to the seat (a deleted seat's history must stay readable).

### 3.3 `api_activitylog.origin` (new, nullable)

`varchar(16) NULL`. New application writes set `origin = 'app'`. Existing rows stay `NULL` and are classified by the registry. The generator sets `origin = 'reconstructed'`. No existing row is updated. `origin` is a technical fact only and carries no attribution.

### 3.4 Resolution rules (per dimension, per row)

1. Collect the entries whose scope (id range, seats, actions, time bounds, marker) matches the row.
2. Drop any entry that another entry names in `supersedes_id`.
3. Prefer the **most specific** remaining entry: more constraining scope fields first, then the narrower id span.
4. If two remaining entries of equal specificity disagree, the **less trusted** value wins (`reconstructed` over `backfilled` over `app_unconfirmed` over `app_preexisting`; `not_human` over `unknown` over `human_confirmed`), the row is flagged as a conflict, and a consistency check fails.
5. A row matching no entry takes the default: provenance `app_unconfirmed` (if `origin` is NULL) or `app` (if `origin = 'app'`); attribution `unknown`.

Downgrades therefore take effect immediately; upgrades to `human_confirmed` need a full attestation.

To stop conflicts being created at all, a database trigger rejects an insert whose scope overlaps an active entry with a different value unless `supersedes_id` names every overlapped active entry.

### 3.5 Append-only enforcement

Model-level guards in Django are a convenience only; they do not stop raw SQL. Enforcement is in the database:

- a `BEFORE UPDATE OR DELETE` trigger on both tables that raises an exception;
- the application role is granted `SELECT` and `INSERT` only on them.

A database superuser can still disable a trigger; that is outside this design and is covered by the host's access control. A test connects as the application role and proves `UPDATE` and `DELETE` fail.

## 4. Access layer: one definition

- `ActivityLog.objects`: unchanged, unfiltered (Django admin, audit, evidence tooling).
- `ActivityLog.analytics(mode)`: returns the queryset for `strict`, `operational` or `audit`, annotated with both axes. It is the **only** supported entry point for analytics.
- **No process-level cache.** The registry is a handful of rows and is read once per request (a single indexed query, memoized for that request). A per-process cache cannot be invalidated across several gunicorn workers or containers (production, staging and QA each run their own), and a few seconds of staleness after an attestation would be an integrity bug. If measurement ever shows a need, the cache key is a fingerprint `(count, max(id))` read by one cheap query per request.
- A static guard test fails the build if an analytics module uses `ActivityLog.objects` outside an explicit allow-list.

## 5. Reader behaviour and presentation

Full table and quantified consequences are in `COMPATIBILITY_ASSESSMENT.md`. Summary:

- Every aggregate shows its composition, never a single unlabelled "genuine" figure: *verified*, *unverified (not independently confirmed)*, and *excluded* (reconstructed, back-filled, demo, administrative) with counts.
- Dashboards, onboarding and recommendations use `operational`. Evaluator-facing reports use `strict` and say "no verified data" when that is the case.
- API responses gain an additive `provenance` object (`mode`, `included`, `counts`, `excluded`), so existing clients keep working.

## 6. Generator guard

`gen_manual_activity.py --apply` must refuse to run without an explicit flag, set `origin = 'reconstructed'` on every row and write the registry entries in the same transaction, with `rows_recorded`. A test asserts this.

## 7. Migration and rollback

### 7.1 Migrations (additive only, per repository policy)

| Step | Change | Row impact |
|---|---|---|
| M1 | create `api_activityprovenance` and `api_seatkind` with their triggers and grants; add nullable `origin` to `api_activitylog` | none. Production is PostgreSQL 16.15, where adding a nullable column with no default is a metadata-only change |
| M2 | idempotent data migration inserting the rule-based and generator entries (reconstructed batch, back-filled 21, pre-batch backup match for ids 1-470, demo companies' seats, administrative actions) | none to `api_activitylog` |
| M3 | later, separately: a partial index for `origin = 'app'`, only if measurement shows a need (`CONCURRENTLY`, outside a transaction) | none |

### 7.2 Pre-flight and verification

Before M1: the evidence backup (`EVIDENCE_PRESERVATION.md`). Record row count, id range, marker count, and a checksum over **the original columns only** (`id, user_id, action, detail, category, car_id, node_title, app_url, created_at`), plus the ordered id list. After M1 and M2 the same values must be identical, and every existing row must have `origin IS NULL`. A checksum that included the table's new column would change by construction and would prove nothing; the test compares the named original columns and asserts the new one is untouched.

### 7.3 Rollback

- **Code:** redeploy the previous image tag (promotion stays a person's action). The previous code ignores the new nullable column and never reads the registry, so it runs against the migrated schema.
- **Schema:** reversing M2 and M1 drops the new tables and column only. Neither touches activity data. Reversal is optional.
- **Data:** nothing to restore, because no activity row is modified.

### 7.4 Performance

The registry has single-digit to low-double-digit entries. The added predicates are `id BETWEEN` terms on the primary key plus the existing `created_at` indexes; at 86,212 rows the cost is negligible. A test records the query plan on 1,000,000 generated rows for bounded windows and fails on a full scan. A feature flag per reader (`KG_ACTIVITY_PROVENANCE_<READER>`) enables the new behaviour one reader at a time on staging, with a shadow comparison first (section 8 of `COMPATIBILITY_ASSESSMENT.md`).

### 7.5 Deletion mechanism (verified)

The seat-to-activity cascade is a Django ORM behaviour. In production the foreign keys are `NO ACTION`, deferrable, initially deferred, so deleting a seat in SQL fails while it owns activity, and deleting it through the ORM first deletes the activity. The registry and the new column do not depend on this and do not change it.

### 7.6 Explicitly out of scope: soft delete and other changes to seat deletion

Making seat deletion non-destructive (soft delete, or a database `RESTRICT`) would address the loss of 18,568 rows, but it changes application behaviour and is **not part of this remediation or of PR #65**. It needs its own proposal and explicit approval. This design only records the mechanism.

## 8. What is not decided here

Which cohorts (if any) become `human_confirmed` is decided only through `ATTESTATION_POLICY.md`, case by case. No block promotion of unverified rows is proposed.

## 10. Deferred decision

Whether the reconstructed rows stay (disclosed, excluded) or are removed later. Removal is a separate change with its own gate, uses the manifest's statements after a verified, restore-tested backup, and records before and after counts first.

## 11. Risks

- Excluding `reconstructed` rows will make wide-window charts fall sharply (about 96% at 365 days). That is intended and must be annotated.
- `unknown` attribution is large and will stay large unless cohorts are attested; dashboards will say so.
- The 181 rows before the batch and the 2 rows with ids <= 8848 but a timestamp after the batch started cannot be classified further.
- If the registry and `origin` ever disagree, the less trusted value wins and a consistency check fails.
