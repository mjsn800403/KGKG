# معماری

## نمای کلی

سیستم از سه لایه‌ی مستقل تشکیل شده است:

1. **خط لوله‌ی داده (Data Pipeline)** — آفلاین/دستی
   - ورودی: آرشیوهای `LEMON *.zip` شامل یک خروجی HTML کامل از دفترچه‌ی یک خودرو.
   - پردازش: `htmlparser_logical.py` هر آرشیو را باز کرده، صفحات را کرال و
     بر اساس breadcrumbها به یک **درخت گره‌ها (nodes)** تبدیل می‌کند و در یک
     دیتابیس SQLite مجزا ذخیره می‌کند.
   - خروجی: یک فایل `.db` به ازای هر خودرو در `KG_backend/Database_warehouse/`،
     تصاویر در `KG_backend/static_warehouse/<car_name>/`، و یک رکورد در جدول
     `main_db` داخل `db.sqlite3`.

2. **بک‌اند (Django)** — لایه‌ی API
   - جدول `main_db` (مدل `Car`) فهرست خودروها را نگه می‌دارد و به فایل دیتابیس
     مخصوص هر خودرو اشاره می‌کند (`db_address`).
   - viewها به‌صورت زنده به دیتابیس SQLite مخصوص هر خودرو وصل می‌شوند
     (با `sqlite3` خام، نه ORM) و گره‌ها را برمی‌گردانند.
   - تصاویر از طریق `/media/` (همان `static_warehouse`) سرو می‌شوند.

3. **لایه‌ی RAG/گراف ارتباطی (`api/rag/`)** — درون همان سرویس Django
   - یک ایندکس محلی و آفلاین (`Database_warehouse/_rag/index.rag.db`) که
     محتوای دفترچه‌ها را به‌صورت **حذف‌تکرارشده** (content-addressed) ذخیره
     و امبد می‌کند و یک گراف ارتباطی بین صفحات می‌سازد. با دستور مدیریتی
     `python manage.py build_rag` ساخته می‌شود (نگاه کنید به
     [assistant.md](assistant.md)).
   - سه endpoint می‌افزاید: `POST/GET /api/assist/` (بازیابی عمومی)،
     `POST/GET /api/diagnose/` (موتور قاعده‌محور DTC/symptom، روی sidecar هر
     خودرو که با `python manage.py build_diag` ساخته می‌شود — **بعد از**
     `build_rag`) و `POST /api/assist/feedback/` (ثبت کلیک کاربر برای
     رتبه‌بندی آینده).

4. **فرانت‌اند (Next.js)** — لایه‌ی نمایش
   - مسیرهای پویا `[brand]/[year]/[model]/[...path]` ساختار درختی را
     قابل‌مرور می‌کنند.
   - یک Route Handler سمت سرور (`/api/chat`) ابتدا از `/api/assist/` بک‌اند
     زمینه‌ی مرتبط (excerpt های دفترچه + گراف ارتباطی) را می‌گیرد، سپس همان
     زمینه را به دستیار هوش مصنوعی Metis می‌دهد تا فقط جمله‌بندی فارسی را
     انجام دهد (کلید API هرگز به مرورگر نمی‌رسد).

## تصمیمات کلیدی طراحی

- **یک دیتابیس به ازای هر خودرو:** درخت هر خودرو در فایل SQLite مستقل خودش
  نگهداری می‌شود؛ `db.sqlite3` فقط نقش فهرست (index) را دارد. این کار باعث
  جداسازی داده‌ها و سادگی افزودن خودروی جدید می‌شود.
- **اتصال خام به SQLite در viewها:** به‌جای مدل‌سازی درخت در Django ORM،
  viewها مستقیم به فایل خودرو وصل می‌شوند چون شِمای گره‌ها توسط پارسر تولید
  می‌شود و خارج از کنترل Django است.
- **پیمایش بر اساس عنوان (title)، نه path:** چون عنوان گره‌ها ممکن است شامل
  «/» باشد (مثل `Service Data [11/2022 - ]`)، مسیر درخت با تطبیق
  `(parent_id, title)` گام‌به‌گام طی می‌شود، نه با مقایسه‌ی رشته‌ی path.
- **ارسال segmentها به‌صورت query param:** به همین دلیل، segmentهای مسیر به‌جای
  قرار گرفتن در path آدرس، به‌صورت پارامترهای تکرارشونده‌ی `seg` ارسال می‌شوند
  تا «/» داخل عنوان با جداکننده‌ی واقعی مسیر اشتباه گرفته نشود.
- **آدرس تصاویر نسبی در بک‌اند:** بک‌اند تصاویر را با مسیر `/media/...` برمی‌گرداند
  و فرانت‌اند آن‌ها را به URL مطلق نسبت به `API_BASE` تبدیل می‌کند؛ بک‌اند نباید
  host/port عمومی خود را بداند.

## فناوری‌ها

| لایه | فناوری |
|------|--------|
| پارسر | Python 3.12، BeautifulSoup + html5lib، sqlite3، ThreadPoolExecutor |
| GUI پارسر | Tkinter |
| بک‌اند | Django ≥4.2، django-cors-headers، SQLite |
| RAG/گراف ارتباطی | sqlite-vec، sentence-transformers (bge-m3 پیش‌فرض)، torch، numpy |
| فرانت‌اند | Next.js 16، React 19، Tailwind CSS 4 |
| دستیار | بازیابی محلی (`api/rag/`) + Metis Chat API برای جمله‌بندی فارسی (پراکسی از طریق Next.js Route Handler) |
