# ۰۹ — رویدادهای بی‌درنگ (SSE)

## ۹٫۱ چرا SSE مبتنی بر پایگاه داده

*(هنگامی نوشته شد که پایگاه داده اصلی SQLite بود؛ از ۲۰۲۶‑۱۰‑۲۹ PostgreSQL با نام `kgkg` است و طراحی تغییر نکرده.)*

برنامه چند فرایند worker گانیکورن + یک worker جداشدهٔ pipeline است، بدون Redis. تنها رسانه‌ای که هر فرایند می‌تواند در آن بنویسد و پایدار دنبالش کند پایگاه داده اصلی است. پس لایهٔ بی‌درنگ این است: جدول فقط‌افزودنی `Event` ← نقطهٔ پایانی SSE آن را دنبال می‌کند ← داشبوردها زنده به‌روز می‌شوند. این دوام و ازسرگیری با `Last-Event-ID` را رایگان می‌دهد؛ بهایش تأخیر دنبال‌کردن ۱ ثانیه است که برای داشبوردها مناسب است. اگر روزی توزیع به مشترکان از آن فراتر رفت فقط پیاده‌سازی دنبال‌کردن عوض می‌شود — پروتکل سیمی ثابت می‌ماند.

## ۹٫۲ انتشار

<div dir="ltr">

```python
from api import events
events.emit(type, payload, audience='admin')          # admins
events.emit_company(type, company_id, payload)        # company dashboards
events.emit_user(type, user_id, payload)              # one user
```

</div>

با بهترین تلاش (هرگز به مسیر درخواست استثنا نمی‌اندازد). جدول به‌صورت سرشکن‌شده تا حدود ۲۰ هزار ردیف برش می‌خورد (تقریباً هر ۵۰۰مین انتشار).

**منتشرکننده‌های فعلی** (انواع رویدادی که به‌صورت فراخوانی literal `emit*` در `KG_backend/api` یافت شد، ۲۰۲۶‑۱۱‑۰۴ **[C]**): worker مربوط به pipeline (`pipeline.progress` با throttle + وضعیت‌های پایانی) و شروع/ازسرگیری/لغو pipeline (`pipeline.started|resumed|canceled`)، هشدارها (`alert.opened`، `alert.resolved`)، ورود + beaconهای فعالیت (پرتال)، درخواست‌های شرکت / میزکار پشتیبانی (`request.created|updated|reopened|rated|message`، برای هر دو مخاطب در جایی که مرتبط است)، بازخورد محصول (`feedback.created`)، تازه‌سازی پیشنهادها (`rec.updated`)، چت پشتیبانی (`support_chat.message|updated|reopened`)، آشکارساز تغییر (`data.detected`، `processing.pending`). *تاریخی:* رویدادهای `team.member.*` و `team.role.*` مربوط به CRUD حذف‌شدهٔ تیم دیگر منتشر نمی‌شوند (`team._emit_team` فراخواننده ندارد).

## ۹٫۳ جریان (`/api/events/stream/`)

- احراز هویت: توکن ادمین (`?admin=1`) یا توکن پرتال؛ کاربران پرتال رویدادهای مخاطب `user` را می‌گیرند، و اگر `can_manage_team` یا `can_view_analytics` داشته باشند مخاطب `company` را هم (`portal_auth.user_can_view_company_stream`).
- پروتکل: فریم‌های استاندارد SSE (`id:`، `event:`، `data:` با JSON ‏`{id,type,ts,payload}`)، توضیح heartbeat هر ۱۵ ثانیه، جریان پس از ۳۰۰ ثانیه بازیافت می‌شود (کلاینت‌ها با مکان‌نما دوباره وصل می‌شوند)، ازسرگیری با هدر `Last-Event-ID` یا `?after=`.
- حلقهٔ دنبال‌کردن پایگاه داده هر ۱ ثانیه. همتای REST با نام `/api/events/recent/?after=` برای جبران عقب‌ماندگی/polling.
- **nginx:** location دقیق `/kg-api/api/events/stream/` دارای `proxy_buffering off` + read timeout برابر ۳۶۰۰ ثانیه است — بدون آن رویدادها در بافر nginx می‌مانند. حذفش نکنید؛ برای هر نقطهٔ پایانی streaming جدید پیکربندی معادل اضافه کنید.
- gunicorn با `--threads 8 --timeout 300` اجرا می‌شود که تا حدی برای نگه‌داشتن همین اتصال‌های طولانی است؛ هر جریان هم‌زمان یک thread را اشغال می‌کند. محدوده: برای ده‌ها داشبورد خوب است، نه هزاران.

## ۹٫۴ مصرف در فرانت‌اند

`src/utils/useEventStream.js` — خوانندهٔ SSE مبتنی بر fetch (EventSource بومی نمی‌تواند هدر Bearer بفرستد): فریم‌ها را پارس می‌کند، مکان‌نما را دنبال می‌کند، با backoff خودکار دوباره وصل می‌شود و وضعیت اتصال را در دسترس می‌گذارد. خود کانکتور `src/utils/eventStreamConnector.js` است (محیط تزریق‌شده، دارای تست واحد): سکوت ۴۵ ثانیه‌ای (سه heartbeat از دست‌رفته) جریان را می‌بندد و دوباره باز می‌کند؛ تلاش‌های ناموفق با ۳، ۶، ۱۲ ثانیه … تا سقف ۶۰ ثانیه با jitter ‏±۲۵٪ عقب می‌روند و پس از بازشدن موفق ریست می‌شوند؛ رویداد `online` مرورگر بلافاصله دوباره وصل می‌کند؛ 401 `unauthorized` گزارش می‌دهد و متوقف می‌شود. صندوق ورودی پشتیبانی تا وقتی به‌روزرسانی زنده قطع است اعلان نشان می‌دهد و بازخوانی ۲۰ ثانیه‌ای خود را نگه می‌دارد. مصرف‌کننده‌ها:

- **AdminDashboard** — KPIها، نوار پیشرفت زندهٔ پردازش، درخواست‌های جدید، هشدارها، فعالیت و نوار رویداد.
- **RequestsInbox** (ادمین) / **RequestsView** (مدیر) — چرخهٔ عمر درخواست در هر دو سو، toast هنگام تکمیل، بدون reload.
- **SupportChatInbox** (`support-chat/admin/`) — رویدادهای `support_chat.*` برای صندوق ورودی کارکنان، با کانکتور مشترک و بازخوانی جایگزین ۲۰ ثانیه‌ای؛ **RecommendationsWidget** — `rec.updated`. *(مصرف‌کنندهٔ قدیمی `TeamView` برای رویدادهای `team.*` با CRUD تیم حذف شد.)*
- **kgkg-detect.timer** (دستور `realtime_tick` هر ۳۰ ثانیه) اثر انگشت کار در انتظار را مقایسه می‌کند تا «داده جدید رسید» بدون کلیک refresh روی داشبورد ادمین ظاهر شود.

## ۹٫۵ افزودن نوع رویداد جدید

۱. یک نام نقطه‌دار (`area.action`) و باریک‌ترین مخاطب را انتخاب کنید.
۲. از بک‌اند هنگام تغییر وضعیت منتشر کنید (درون try/except — با بهترین تلاش).
۳. در مصرف‌کننده با `useEventStream` مدیریت کنید (switch روی `type` در `onEvent`).
۴. اینجا و در `docs/CHANGELOG.md` مستند کنید.
